# Handoff — page-boundary options, and mixed-evidence folders

Written 2026-07-30 for the agent picking these up. Two independent defects,
both found while diagnosing something else. Neither is fixed. Read
[CLAUDE.md](../CLAUDE.md) first for the project rules.

Every claim below is marked **VERIFIED** (I checked the code or rendered the
page) or **HYPOTHESIS** (plausible, untested). Do not promote a hypothesis to
fact without checking it — one earlier investigation in this repo cost a day by
theorising from model output instead of rendering the document
([ANSWER_LAYOUTS.md](ANSWER_LAYOUTS.md) records that lesson).

## Issue 1 — a question's options are truncated at a page break

### What the tutor sees

Three confirmed instances, all the same shape:

| Document | Question | Symptom |
|---|---|---|
| `EOR IM MCQ 2025-194-2nd (2) 1.pdf` p3→p4 | 19, "safest drug for hypertension in pregnancy" | options a–c extracted, **d. Methyldopa** (top of p4) missing; tutor edited by hand |
| `IM FINAL MCQ 6TH 2025.pdf` p7→p8 | 41, "iron regulatory hormone" | only a) Ferritin, b) Transferrin extracted; c/d are on p8 |
| same folder | reported generally | "didn't extract questions as well" |

The question prompt and the first options sit at the bottom of page N; the
remaining options continue at the top of page N+1. Only the page-N part
survives.

### Why nothing catches it — **VERIFIED**

- `extendClippedOptionBoxes` ([assemble.ts](../src/engine/assemble.ts)) is the
  deterministic repair for clipped option boxes, but it is explicitly bounded
  **within one page**: `OPTIONS_FOOTER_LIMIT = 975` stops the box short of the
  footer so a page number is never boxed as an option. It cannot reach page N+1.
- `regions.options` is a single `Region` with a single `page`. The data model
  has no way to express "options span two pages."
- `underTranscribedRowIds` ([executor.ts](../src/engine/executor.ts)) only
  re-asks rows with **fewer than 2 options**. Q41 came back with exactly 2, so
  it looks like a legitimate True/False-shaped row and is never retried. This is
  deliberate — the comment says partial drops (3-of-5) are indistinguishable
  from genuinely short questions — but it is exactly why this bug is silent.

### The most promising lead — **HYPOTHESIS**

`source_pages` is already the mechanism that decides which page images a worker
chunk receives (`chunkPages` in [blueprint.ts](../src/engine/blueprint.ts)
unions every row's `source_pages`). The INDEX prompt already asks for "every
source_pages image needed to transcribe it". So:

1. Check what INDEX actually returned for Q41 — does `sourcePages` contain
   `[7]` or `[7,8]`? (Snippet below.) If it says `[7]`, INDEX is
   under-reporting the continuation page.
2. If the worker already receives page 8 and still drops the options, the fix is
   not `source_pages` — it is that the options *region* points only at page 7
   and the worker follows it.

A deterministic detector is available either way: an options box whose bottom
edge reaches `OPTIONS_FOOTER_LIMIT` with no following question on that page is
*probably* clipped by the page break, and its owner row could have page N+1
appended to `source_pages`. That is code, not a prompt change.

**Cost to weigh:** widening `source_pages` puts another full page image into
that chunk's request. Measure the quota impact before shipping it broadly.

## Issue 2 — folders mixing separate-key and inline-answer PDFs

### The setup

One folder, several exam PDFs. Some have a separate answer-key PDF attached in
the card's key slot; others have the answers handwritten on the pages
themselves. The tutor reports the folder behaving worse than single files.

### What is sound — **VERIFIED**

Per-PDF key pairing is correct and transactional. `putAnswerKeyPdf`
([files.ts](../src/state/files.ts)) stores the key with a `parentPdfId`,
replaces only that exam's previous key, and "never touches another exam's key";
`answerKeyFor` looks it up by the same id. A folder where some PDFs have keys
and others don't is a supported configuration, not a misuse. **Do not start by
suspecting the pairing.**

### The actual hazard — **HYPOTHESIS, and the first thing to test**

The document-level answer policy is all-or-nothing per run, and the EVIDENCE
stage overrides the inline observation:

- With **no** key attached, policy comes from INDEX:
  `answerPresent` on any question ⇒ `inline_marks`
  ([executor.ts](../src/engine/executor.ts), `defaultEvidence`).
- With a key attached, `runEvidence()` runs the EVIDENCE call and **its** parsed
  `type` becomes the document policy. A parse failure falls back to
  `defaultEvidence`, but a *successful* response saying `uncertain` or
  `no_answer_key` does not.
- `forceAnswer` ([merge.ts](../src/engine/merge.ts)) checks the document policy
  **first**: `no_answer_key` or `uncertain` blanks **every row**, before any
  per-row logic runs.

So: a PDF that has both a separate key *and* inline marks, whose EVIDENCE call
returns `uncertain`, loses **every answer** — including the inline ones INDEX
correctly saw. The per-ref fallback in `assemble.ts`
(`keyEvidence?.state ?? (answerPresent ? 'inline' : 'none')`) cannot rescue it,
because the document-level gate fires earlier.

Test it by reading the run's `blueprint-valid` artifact and looking at
`document_profile.answer_policy.type` for each PDF in the folder.

### Extra context that matters

`Docs/ANSWER_LAYOUTS.md` still lists **"a real separate answer-key document,
verified end-to-end"** under *Still uncovered*. The separate-key path has never
been confirmed working on a real document. If the tutor's first PDF used a key
file, its results may be the first real exercise of that path — treat its
output as unproven rather than as a regression.

## Tools you will want

**Render a page before theorising about it:**

```
node scripts/render-pdf-pages.mjs "<file.pdf>" 7 8
```

Writes `scripts/out/page-N.png` using the same renderer the engine uses. The
tutor's PDFs are in `~/Downloads/Telegram Desktop/`.

**Read a real run's stored artifacts** (no quota spent). In the app's DevTools
console, on the same origin the run happened:

```js
(async () => {
  const db = await new Promise((res,rej)=>{const r=indexedDB.open('codox');r.onsuccess=()=>res(r.result);r.onerror=()=>rej(r.error)})
  const all=(s)=>new Promise((res,rej)=>{const r=db.transaction(s).objectStore(s).getAll();r.onsuccess=()=>res(r.result);r.onerror=()=>rej(r.error)})
  const runs=await all('runs'), arts=await all('runArtifacts')
  console.table(runs.map((r,i)=>({i, file:r.fileName, status:r.status, flagged:r.flaggedRows})))
  window.__pick=(i)=>{
    const run=runs[i], a=arts.filter(x=>x.runId===run.id)
    window.__d={run, blueprint:a.find(x=>x.kind==='blueprint-valid')?.json,
      index:a.find(x=>x.kind==='index-reconcile')?.json,
      merged:a.find(x=>x.kind==='merged-rows')?.json,
      reqs:a.filter(x=>x.kind==='chunk-request').sort((p,q)=>p.chunkIndex-q.chunkIndex),
      resps:a.filter(x=>x.kind==='chunk-response').sort((p,q)=>p.chunkIndex-q.chunkIndex)}
    console.log(run.fileName,'policy',__d.blueprint?.document_profile?.answer_policy)
  }
  console.log('run __pick(i)')
})()
```

For issue 1: `__d.index.questions.find(q => q.printedLabel === '41').sourcePages`
and the same row's `regions.options` in `__d.blueprint.planned_rows`.
For issue 2: `__d.blueprint.document_profile.answer_policy` per run.

Artifacts are never pruned automatically, so the failing runs are still on the
tutor's device.

## Project rules you must not trip over

- **The three prompts are SHA-pinned.** `prompts.test.ts` checks the constant,
  the `Docs/CODOX_MIGRATION.md` block, and the hash in `PROMPT_SHA256` all
  agree. Editing one means updating all three together, and it needs the
  owner's say-so. Both issues here look fixable in deterministic code — prefer
  that.
- **Shipping means pushed to `main`.** That one push deploys web, the Windows
  auto-updater, and the Android update banner. A local-only fix repairs one
  machine and leaves every other device broken.
- **COST-ZERO and one user key.** Any fix that adds model calls costs the
  tutor's own free-tier quota (they watch a 400/day counter). Extra page images
  per chunk are a real cost — measure.
- **NEVER-GUESS was retired as doctrine on 2026-07-30** (owner call, commit
  `9675f54`). The deterministic guards in `forceAnswer` still exist and still
  run; they were kept deliberately. Do not reintroduce the doctrine language,
  and do not remove the code guards without asking.

## What is already done — do not redo it

Same session, already shipped: the worker was dropping `correct_index` for
entire requests at a time (8 of 22 chunks on two surgery exams, all answers
blank, perfect question text). Cause was that the WORKER prompt only ever
*forbade* answering and never told the model to look for a mark. Fixed by an
owner-approved prompt edit (commit `53bf5e9`, new worker SHA `274e8002…`).
An earlier attempt that appended a hedging-heavy directive instead measured
**worse** and was reverted — do not re-add "leave it blank" hedging to that
prompt.

That work is unrelated to both issues above beyond touching the same files.
