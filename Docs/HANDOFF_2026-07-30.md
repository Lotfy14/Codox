## Issue 1 — a question's options are truncated at a page break

### What the tutor sees

Three confirmed instances, all the same shape:

| Document | Question | Symptom |
|---|---|---|
| `EOR IM MCQ 2025-194-2nd (2) 1.pdf` p3→p4 | 19, "safest drug for hypertension in pregnancy" | options a–c extracted, **d. Methyldopa** (top of p4) missing; tutor edited by hand |
| `IM FINAL MCQ 6TH 2025.pdf` p7→p8 | 41, "iron regulatory hormone" | only a) Ferritin, b) Transferrin extracted; c/d are on p8 |
| same folder | reported generally | "didn't extract questions as well" |

The question prompt and the first options sit at the bottom of page N; the
remaining options continue at the top of page N+1. Only the page-N part
survives.

### Why nothing catches it — **VERIFIED**

- `extendClippedOptionBoxes` ([assemble.ts](../src/engine/assemble.ts)) is the
  deterministic repair for clipped option boxes, but it is explicitly bounded
  **within one page**: `OPTIONS_FOOTER_LIMIT = 975` stops the box short of the
  footer so a page number is never boxed as an option. It cannot reach page N+1.
- `regions.options` is a single `Region` with a single `page`. The data model
  has no way to express "options span two pages."
- `underTranscribedRowIds` ([executor.ts](../src/engine/executor.ts)) only
  re-asks rows with **fewer than 2 options**. Q41 came back with exactly 2, so
  it looks like a legitimate True/False-shaped row and is never retried. This is
  deliberate — the comment says partial drops (3-of-5) are indistinguishable
  from genuinely short questions — but it is exactly why this bug is silent.

### The most promising lead — **HYPOTHESIS**

`source_pages` is already the mechanism that decides which page images a worker
chunk receives (`chunkPages` in [blueprint.ts](../src/engine/blueprint.ts)
unions every row's `source_pages`). The INDEX prompt already asks for "every
source_pages image needed to transcribe it". So:

1. Check what INDEX actually returned for Q41 — does `sourcePages` contain
   `[7]` or `[7,8]`? (Snippet below.) If it says `[7]`, INDEX is
   under-reporting the continuation page.
2. If the worker already receives page 8 and still drops the options, the fix is
   not `source_pages` — it is that the options *region* points only at page 7
   and the worker follows it.

A deterministic detector is available either way: an options box whose bottom
edge reaches `OPTIONS_FOOTER_LIMIT` with no following question on that page is
*probably* clipped by the page break, and its owner row could have page N+1
appended to `source_pages`. That is code, not a prompt change.

**Cost to weigh:** widening `source_pages` puts another full page image into
that chunk's request. Measure the quota impact before shipping it broadly.

## Issue 2 — folders mixing separate-key and inline-answer PDFs

### The setup

One folder, several exam PDFs. Some have a separate answer-key PDF attached in
the card's key slot; others have the answers handwritten on the pages
themselves. The tutor reports the folder behaving worse than single files.

### What is sound — **VERIFIED**

Per-PDF key pairing is correct and transactional. `putAnswerKeyPdf`
([files.ts](../src/state/files.ts)) stores the key with a `parentPdfId`,
replaces only that exam's previous key, and "never touches another exam's key";
`answerKeyFor` looks it up by the same id. A folder where some PDFs have keys
and others don't is a supported configuration, not a misuse. **Do not start by
suspecting the pairing.**

### The actual hazard — **HYPOTHESIS, and the first thing to test**

The document-level answer policy is all-or-nothing per run, and the EVIDENCE
stage overrides the inline observation:

- With **no** key attached, policy comes from INDEX:
  `answerPresent` on any question ⇒ `inline_marks`
  ([executor.ts](../src/engine/executor.ts), `defaultEvidence`).
- With a key attached, `runEvidence()` runs the EVIDENCE call and **its** parsed
  `type` becomes the document policy. A parse failure falls back to
  `defaultEvidence`, but a *successful* response saying `uncertain` or
  `no_answer_key` does not.
- `forceAnswer` ([merge.ts](../src/engine/merge.ts)) checks the document policy
  **first**: `no_answer_key` or `uncertain` blanks **every row**, before any
  per-row logic runs.

So: a PDF that has both a separate key *and* inline marks, whose EVIDENCE call
returns `uncertain`, loses **every answer** — including the inline ones INDEX
correctly saw. The per-ref fallback in `assemble.ts`
(`keyEvidence?.state ?? (answerPresent ? 'inline' : 'none')`) cannot rescue it,
because the document-level gate fires earlier.

Test it by reading the run's `blueprint-valid` artifact and looking at
`document_profile.answer_policy.type` for each PDF in the folder.

### Extra context that matters

`Docs/ANSWER_LAYOUTS.md` still lists **"a real separate answer-key document,
verified end-to-end"** under *Still uncovered*. The separate-key path has never
been confirmed working on a real document. If the tutor's first PDF used a key
file, its results may be the first real exercise of that path — treat its
output as unproven rather than as a regression.

## Project rules you must not trip over

- **The three prompts are SHA-pinned.** `prompts.test.ts` checks the constant,
  the `Docs/CODOX_MIGRATION.md` block, and the hash in `PROMPT_SHA256` all
  agree. Editing one means updating all three together, and it needs the
  owner's say-so. Both issues here look fixable in deterministic code — prefer
  that.
- **Shipping means pushed to `main`.** That one push deploys web, the Windows
  auto-updater, and the Android update banner. A local-only fix repairs one
  machine and leaves every other device broken.
- **COST-ZERO and one user key.** Any fix that adds model calls costs the
  tutor's own free-tier quota (they watch a 400/day counter). Extra page images
  per chunk are a real cost — measure.
- **NEVER-GUESS was retired as doctrine on 2026-07-30** (owner call, commit
  `9675f54`). The deterministic guards in `forceAnswer` still exist and still
  run; they were kept deliberately. Do not reintroduce the doctrine language,
  and do not remove the code guards without asking.

## What is already done — do not redo it

Same session, already shipped: the worker was dropping `correct_index` for
entire requests at a time (8 of 22 chunks on two surgery exams, all answers
blank, perfect question text). Cause was that the WORKER prompt only ever
*forbade* answering and never told the model to look for a mark. Fixed by an
owner-approved prompt edit (commit `53bf5e9`, new worker SHA `274e8002…`).
An earlier attempt that appended a hedging-heavy directive instead measured
**worse** and was reverted — do not re-add "leave it blank" hedging to that
prompt.

## Resolution (2026-07-30)

Both fixed in deterministic code. No prompt was edited — the three pinned
prompts and the output contract are untouched, and INDEX/EVIDENCE were not
touched either.

### Issue 1 — page-boundary options

The hypothesis about `source_pages` was **not** pursued as a blueprint-wide
change, and the reason is cost: widening `source_pages` at planning time puts
an extra page image into every worker chunk of every run, and the tutor pays
for those out of their own free-tier quota. The widening is confined to a
targeted re-ask instead.

- `pageBoundaryOptionRowIds` ([assemble.ts](../src/engine/assemble.ts)) names
  the rows whose options are the last thing on their page and that have a page
  after them. It reuses the column/geometry logic
  `extendClippedOptionBoxes` already had — that function was refactored onto a
  shared `nextQuestionTopBelowOptions` helper and its behaviour is byte-for-byte
  unchanged (the footer limit is still the floor; existing tests still pass).
- `underTranscribedRowIds` ([executor.ts](../src/engine/executor.ts)) keeps its
  old "<2 options" rule and adds a second: a page-boundary row that came back
  with **fewer options than the document's own `modalOptionCount`**. Both
  signals are required. This is exactly the gap the original write-up
  identified — 2-of-4 at a page break is no longer indistinguishable from a
  True/False, because the geometry says otherwise.
- `repairUnderTranscribedRows` gives such a row page N+1 (image *and* a widened
  `source_pages` in its reduced blueprint) so the re-ask can actually see the
  continuation. It still accepts only a strictly longer result.

- Because recovery is not guaranteed (see the measurements below), a row that is
  STILL short after the re-ask is flagged `options_cut_at_page_break` in
  `executeRun`. That flag is the actual guarantee: a truncated question can
  never ship as if it were whole. It matters most on an answered exam, where
  such a row would otherwise carry a real `correct_index` into an option list
  that is missing the right answer, and pass unflagged.

**The `source_pages` hypothesis was tested and is NOT the cause.** Chunk
requests on the measured document already contained the continuation page every
time — chunk 1 = rows 11–20, pages [2,3]; chunk 2 = rows 21–30, pages [4,5];
chunk 4 = rows 41–47, pages [7,8]. Row 41 was transcribed correctly from those
same images in one run while rows 11 and 23 were not. The image was never
missing; the worker follows the single-page `regions.options` and stops. The
widening is kept because a boundary row that is the last row of its chunk can
genuinely lack the next page, but it is not the operative fix — do not
re-derive this.

Also unfixed by design: a document whose option counts have no majority gets no
norm, so only the old <2 rule runs there.

### Issue 2 — mixed-evidence folders

The hypothesis was correct, and the mechanism is confirmed in code. Fixed at
the source of the bad label rather than by weakening `forceAnswer`.

- `keepIndexObservedMarks` ([executor.ts](../src/engine/executor.ts)) — pure,
  exported, called only from `runEvidence`. When EVIDENCE (which only ever
  reads the **key** pages) returns `uncertain` or `no_answer_key` *and* INDEX
  saw marks on the **exam** pages, the document type becomes `mixed`.
- `forceAnswer`'s document-level veto is **kept unchanged**. `mixed` is in
  `EVIDENCE_POLICY_TYPES`, so the row's own policy decides: no observed
  evidence still blanks `no_visible_answer`, an illegible per-ref key state
  still blanks `key_unclear`, and every worker value is still range-checked.
- One label fixes both halves. The worker is *also* handed the document policy
  and its prompt says to leave `correct_index` empty when the policy reads
  `uncertain` — so the old label suppressed the answer at the model too, not
  only at merge.
- A run where this fires logs `engine.evidence.mixed` with both the key's
  verdict and the document's.

**Still unproven:** the separate-key path itself, exactly as the original
write-up said — `ANSWER_LAYOUTS.md` still lists it under *Still uncovered*.
This fix stops an unreadable key from destroying on-page answers; it does not
demonstrate that reading a REAL key works.

## Verification — measured on the real document, 2026-07-30

Three live conversions of `IM Final MCQ 6th 2025.pdf` (8 pages, 47 questions,
a photographed paper with handwritten ticks), driven headless through the real
app via `scripts/cli-convert.mjs`. Pages were rendered and read first — the
document does the thing: **every** page ends with a question whose options
continue at the top of the next page (Q41 → "c) Erythropoietin, d) Hepcidin" is
literally the first line of page 8; Q11 → "d- Rigidity" is the first line of
page 3; Q23 → "c) Nephrotic syndrome, d) Right heart failure" opens page 5).

**Detection is exact.** `pageBoundaryOptionRowIds` named 7 rows — one per page
for pages 1–7, correctly excluding page 8 (no page after it) — in both runs
where it was checked, with **zero false positives**. `modalOptionCount` read 4
(37 of 47 rows). Rows 15 and 45 have genuinely 3 printed options mid-page and
were correctly left alone; row 44 has 5 and was left alone.

**Recovery works, but not every time.** Five re-asks of page-boundary rows
across the runs: rows 11 (3→4, "Rigidity" read off page 3 — verified against
the render) and 41 (2→4, the exact question from the original report) were
**recovered**; row 23 failed all three attempts and was flagged. So both halves
earn their place — the re-ask fixes some, the flag catches the rest.

**The flag does the job it was added for.** In run 2, row 23 came back with 2 of
4 options AND `correct_index: "1"` — a question that would have exported
looking complete while missing the right answer. It shipped flagged
`options_cut_at_page_break` instead. Row 47 (bottom of the last page, options
continue onto a page this PDF does not contain) came back with 1 option and was
flagged `incomplete_options`. In run 1 the worker had *invented* three
plausible options for that same row 47 — a reminder that the flag is protecting
against a real failure mode.

**Issue 2 reproduced and fixed.** Run 3 attached a deliberately unreadable
one-page "answer key". The log records both sides of the fix:
`engine.evidence.mixed` with `{keyPolicy: "no_answer_key", documentPolicy:
"mixed"}`, and the final blueprint carries `answer_policy.type: "mixed"`. 11 of
47 rows kept an answer. Pre-fix, `forceAnswer`'s first branch would have seen
`no_answer_key` and blanked **all 47** — the reported defect exactly.

### Known interaction — the AUDIT does not know about page boundaries

The audit checks a row's options against the blueprint's single-page regions,
so an option legitimately recovered from page N+1 reads to it as an invention.
Run 2: *"Option 'Rigidity' was added by worker, which is not present in the
planner or source image 2"* — but Rigidity IS printed, at the top of page 3.
The complaint is a false positive and it contributes to `notSafeToImport`.

Deliberately NOT worked around: the AUDIT prompt is SHA-pinned (owner call),
and suppressing "options added" failures in code would also suppress genuine
invention reports. It also sits inside the audit's existing noise floor on this
document — the same run flagged rows 24, 25 and 26 the same way and those rows
were never re-asked, while run 3 raised no options complaints at all despite
recovering rows. Worth an owner decision, not a silent code workaround.
